# 0078 문서 폴더를 쓸 수 없으면 홈 폴더 아래로 내려가고 한 번 알린다

## 맥락

2026-10-26과 27일에 "설치하고 처음 켜면 응답없음", "환영 화면에서 '다음'을 누르면 멈춘다", "회색 화면만 나온다"는 신고가 의견 보내기와 질문 도우미로 열 건 넘게 들어왔다(Windows 10·11, 0.12.4부터 0.12.6까지). 한 신고자는 회사 PC에서 로그를 보고 원인을 짚었다. 앱이 `문서\IeumOffice` 폴더를 만들려고 하면 Windows 보안의 '제어된 폴더 액세스'(랜섬웨어 방지)가 막고, 앱이 같은 일을 되풀이한다. 앱을 그 설정의 허용 목록에 넣자 정상으로 돌아갔다.

코드도 그렇게 되어 있었다. 기본 저장 폴더는 `configuredDefaultSaveDir`가 부를 때마다 정하는데, 폴더가 이미 있어도 매번 `mkdirSync`를 불렀고, 대체 폴더(`문서\IeumOffice`)를 쓸 수 없으면 예외를 던졌다. 이 함수는 홈 화면의 폴더 나무, 폴더 감시, 검색 색인, 모든 편집기의 첫 저장이 쉬지 않고 부른다. 막힌 PC에서는 그때마다 동기 폴더 만들기가 막히고(차단 알림도 그만큼 뜬다) 예외가 났다. 홈 화면의 폴더 요청은 실패를 다루지 않는다.

## 결정

- **있는 폴더는 다시 만들지 않는다.** `isUsableSaveDir`는 폴더가 없을 때만 만들고, 있으면 쓰기 권한만 본다.
- **쓸 수 없던 폴더는 30초 동안 다시 시도하지 않는다.** 실패를 프로세스 전역(`Symbol.for`)에 적어 두므로, 편집기마다 따로 번들에 든 사본도 같은 기록을 본다. 30초가 지나면 다시 시도하므로, 사용자가 앱을 허용하면 다시 켜지 않아도 문서 폴더로 돌아간다.
- **대체 폴더를 차례로 내려간다.** `문서\IeumOffice` → `<홈>\IeumOffice` → `<앱 데이터>\IeumOffice`. 홈 폴더는 '제어된 폴더 액세스'가 기본으로 지키는 폴더가 아니다. 앱 데이터 폴더는 앱이 늘 쓸 수 있으므로, 예외는 사실상 나지 않는다. 사용자가 저장 위치를 정해 두었으면 지금처럼 그 폴더를 먼저 쓴다.
- **내려갔으면 한 번 알린다.** 홈 화면이 폴더 나무를 처음 읽을 때, 어느 폴더를 못 썼고 새 파일이 어디에 저장되는지, 허용하는 곳과 설정 › 일반 › 저장 위치를 경고 창으로 알린다(실행마다 한 번, 21개 언어).

## 버린 대안

- **설치 프로그램이 앱을 '제어된 폴더 액세스' 허용 목록에 넣기.** 관리자 권한과 보안 설정 변경이 필요하고, 사용자가 모르는 사이 보안 설정을 바꾸는 일이다. 회사 PC는 정책으로 막혀 있기도 하다.
- **처음부터 앱 데이터 폴더를 기본으로 쓰기.** 탐색기에서 찾기 어렵고, 모든 사용자의 저장 위치가 바뀐다.
- **예외를 던지되 홈 화면이 오류를 다루기.** 첫 저장, AI 결과 저장, 검색 색인이 모두 같은 함수를 지나므로 화면 하나만 고쳐서는 앱을 쓸 수 없다.

## 결과

- 문서 폴더가 막힌 PC에서도 앱이 뜨고, 새 파일은 홈 폴더 아래에 저장된다. 사용자는 이유와 푸는 방법을 한 번 본다.
- 이미 `문서\IeumOffice`가 있는데 '제어된 폴더 액세스'가 쓰기만 막는 경우는 그대로다. 쓰기 권한 검사는 그 차단을 보지 못한다. 저장할 때의 오류 글과 도움말의 허용 안내에 기댄다.
- 남은 확인: '제어된 폴더 액세스'를 켠 Windows에서 실제로 앱이 뜨는지와 알림 창은 시험 사용자 PC나 신고자에게 확인을 부탁한다. 멈춤의 원인이 이것 하나인지는 아직 모른다.
- 2026-10-28 확인: 0.12.8도 '제어된 폴더 액세스'를 켠 Windows 11에서 시작하자마자 응답없음이 됐다. 막힌 폴더 만들기가 `ENOENT`(부모가 있는데도)로 실패하고, Node의 `mkdirSync(dir, { recursive: true })`가 그 오류를 받고 끝없이 다시 시도해 뒷단이 CPU 한 코어를 쓴 채 멈췄다. 그래서 30초 건너뛰기와 대체 폴더에 닿기 전에 멈췄다. 가장 가까운 있는 상위 폴더부터 한 단계씩 `recursive` 없이 만들도록 바꿨다.
