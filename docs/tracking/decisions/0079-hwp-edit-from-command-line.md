# 0079 — 터미널 명령어로 한글 문서를 만들고 고친다. 연산은 편집기 AI의 도구를 그대로 쓴다

[0023](0023-hwp-read-outside-editor.md)의 "편집기 밖에서는 읽기만 한다"를 터미널 명령어와 그 MCP에 한해 바꾼다. 앱 안에서 편집기 밖의 길(파일 검색, 첨부, 앱 안 MCP)은 그대로 읽기만 한다.

## 맥락

명령어는 워드·엑셀·파워포인트·ODT 문서를 만들고 고치지만, 한글 문서는 `hwp read`로 읽기만 했다. 코딩 에이전트에게 "이 양식을 채워 달라", "회의록을 한글 파일로 만들어 달라"고 하면 막혔다. 저장소 주인이 이것을 할 수 있어야 한다고 했다(2026-10-27).

0023이 고치기를 뺀 이유는 둘이었다. 편집기 안에서는 변경 하나가 실행 취소 한 단계이고 개체를 잃는 변경을 되돌리는 보호가 있는데, 화면 없이 파일을 고치면 그 보호가 없다. 또 저장 결과를 한컴 한글에서 여는 확인을 하지 않았다.

그 사이에 확인된 것:

- 편집기 AI의 도구(`apps/hwp/src/renderer/ai/hwp-skill.ts`)와 그 도구가 부르는 플러그인(`apps/hwp/studio-plugin/agent-plugin.mjs`)은 편집기 없이 node에서 실제 엔진으로 돈다. 플러그인 테스트가 이미 그렇게 돈다. 플러그인이 기대는 호스트는 읽기, 변경 묶음, 이벤트 셋뿐이다.
- 편집기의 변경 묶음은 엔진의 스냅숏 호출(`saveSnapshot`·`restoreSnapshot`)로 되돌린다. 같은 호출로 호스트를 만들면 플러그인의 보호(개체·누름틀 수를 견주고 다르면 던져서 되돌리기, 메모를 지울 변경의 거절)가 그대로 선다.
- 앱의 저장 바로잡기(`apps/hwp/src/main/save-fixes.ts`와 그것이 부르는 모듈)는 Electron 없이 바이트만 다룬다.
- 명령어로 새로 만든 `.hwp`·`.hwpx`와, 테스트 견본(한컴으로 만든 교과협의록 양식, rhwp의 공개 재현본인 메모·각주·머리말·표 52개가 든 40쪽 문서, 머리말·꼬리말 표가 든 HWPX, 메모가 든 HWPX)을 명령어로 고친 파일을 한컴 한글 2024로 열었다(`tools/odt-hancom/hancom.py look`). 모두 열렸고, 개체 수(표, 그림, 메모, 각주, 머리말·꼬리말)가 원본과 같았다.

## 결정

- `ieumoffice hwp apply <파일> --ops`(MCP `hwp_apply`)로 있는 문서를 고치고, `ieumoffice create --type hwp|hwpx --ops`(MCP `create_hwp`)로 새 문서를 만든다. 새 문서는 엔진의 빈 문서(A4 한 쪽, 빈 문단 하나)에서 시작한다. 새 한글 탭과 같다.
- 연산은 편집기 AI의 도구를 그대로 쓴다. 연산 하나는 `{ "op": <도구 이름>, ...도구 입력 }`이고, 답은 AI가 받는 글 그대로다. 명령어 쪽에 도구의 두 번째 구현을 만들지 않는다. 연산 목록(`ieumoffice guide hwp`, MCP의 `hwp-ops` 형식)도 도구 정의에서 만든다.
- 화면·네트워크·모델이 필요한 도구(웹 읽기, 그림 찾기·만들기, 그림 넣기, 편집기 선택 도구)는 명령어에 없다. 부르면 `unsupported`로 거절한다.
- 메모를 지울 변경은 앱에서 사람에게 묻는다. 명령어에는 물을 사람이 없으니 거절한다.
- 묶음은 다른 문서 명령처럼 기본이 "하나라도 거절되면 아무것도 쓰지 않음"이고, `--best-effort`·`--stop-on-error`·`--dry-run`을 받는다. 읽기 연산만 든 묶음은 파일을 쓰지 않는다.
- 저장은 앱의 저장과 같은 순서다. 연 형식 그대로 쓰고, `--out`이면 그 확장자의 형식으로 쓴다. `.hwp`는 엔진이 다시 읽어 쪽수가 같을 때만 쓴다. 새 탭 폭, 필드 종류, 구역 뒤 바탕쪽·메모, 수식 캡션을 바로잡는다(0024, 0026, 0028). 결과가 그 형식의 컨테이너인지 본다. HWPX는 빠진 메모 수를 알린다. 덮어쓰는 파일은 먼저 `<파일 이름>.bak`으로 남긴다. 명령 한 번이 앱의 탭 하나와 같아서, 실행할 때마다 그 직전 파일이 `.bak`이 된다.
- 열 때도 앱과 같다. 변경 추적이 든 `.hwp`는 지금의 내용으로 열고(0027) 결과에 경고로 알린다. 그렇게 할 수 없는 파일과 암호가 걸린 문서는 `unsupported`로 거절한다.
- 앱이 탭으로 연 파일은 다른 형식처럼 `--force` 없이 쓰지 않는다.

## 택하지 않은 것

- **명령어 쪽에 한글 연산을 따로 만든다.** 플러그인이 지키는 규칙(찾은 말이 여러 곳이면 고르지 않기, 개체 있는 문단을 지우지 않기, 칸 채우기는 전부 아니면 전무)을 다시 구현하고 따로 유지해야 한다. 같은 요청에 앱과 명령어가 다르게 고칠 수 있다.
- **편집기 창을 숨겨 띄워 고친다.** 파일 하나에 렌더러를 띄우고, 화면 없는 PC나 Linux 서버에서 돌지 않는다. 플러그인은 편집기 없이 돈다.
- **편집기의 스냅숏 대신 문서를 통째로 내보냈다 다시 읽어 되돌린다.** 플러그인 테스트가 쓰는 방식이지만, `.hwpx` 문서를 HWP 바이트로 되돌리면 그 뒤 HWPX로 내보낼 때 원래 문서와 달라질 수 있다.
- **메모를 지워도 되는 옵션을 둔다.** 첫 판에서는 뺀다. 지금은 거절과 그 메모 목록을 돌려주고, 필요해지면 그때 더한다.

## 결과

- 한글 편집기의 도구 정의·플러그인·저장 모듈을 고치면 명령어의 동작도 바뀐다. `apps/hwp/AGENTS.md`와 `packages/cli/AGENTS.md`에 적었고, `packages/cli/tests/hwp-apply.test.ts`가 실제 엔진으로 지킨다.
- 도구의 설명은 앱 AI를 위해 쓴 글이라 "사용자", "실행 취소" 같은 말이 나온다. 명령어에서도 뜻은 통하므로 그대로 둔다.
- 명령어 쪽 MCP의 도구 목록 크기 상한을 99KiB에서 112KiB로, 형식을 빼는 경우의 상한을 45KiB에서 48KiB로 올렸다. `hwp_apply`의 연산 형식이 약 10KiB다. `create_hwp`는 같은 형식을 두 번 싣지 않으려고 연산 형식을 적지 않고 `hwp_apply`의 모양이라고만 알린다.
- 한컴 확인은 이번에 견본 여섯 개로 했다. 그림·글상자가 많은 실제 공문서의 고치기는 사람의 사용으로 더 본다.
